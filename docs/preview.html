Problem Analysis

تحليل المشكلة هو إنك تفهم المطلوب، وتحدد البيانات والوظائف والقيود، قبل ما تبدأ في تصميم الحل وتنفيذه. مثلًا، طلب «برنامج ينظم المكتبة» يحتاج توضيح الكتب والأعضاء والاستعارة والإرجاع والتقارير قبل كتابة الكود.

مثال نظام المكتبة

المستخدم

موظف المكتبة، وربما الأعضاء.

المشكلة

صعوبة متابعة الكتب المستعارة والمتاحة.

الهدف

تنظيم بيانات الكتب وحركة الاستعارة.

النتيجة

معرفة حالة كل كتاب وتسجيل عمليات الاستعارة والإرجاع.

مقارنة المتطلبات

المتطلبات الوظيفية تحدد ما الذي يفعله النظام، أما المتطلبات غير الوظيفية فتحدد جودة التنفيذ والقيود التي يلتزم بها.

Functional Requirements

المتطلبات الوظيفية

السؤال: النظام المفروض يعمل إيه؟

  • إضافة كتاب وتعديل بياناته.
  • حذف كتاب وفق صلاحيات محددة.
  • البحث عن الكتب.
  • تسجيل الاستعارة والإرجاع.
  • عرض حالة كل كتاب.

Non-Functional Requirements

المتطلبات غير الوظيفية

السؤال: بأي جودة ومستوى ينفذ النظام وظائفه؟

  • سهولة الاستخدام.
  • سرعة الاستجابة.
  • حماية بيانات المستخدمين.
  • استخدام النظام من أجهزة مختلفة.
  • الحفاظ على البيانات وعدم فقدانها.

تحليل برنامج درجات الطلاب

المطلوب: برنامج يستقبل درجات الطالب في ثلاث مواد، ويحسب المتوسط، ويحدد هل حقق درجة النجاح أم لا.

الهدف والمدخلات

حساب المتوسط وتحديد الحالة. المدخلات: الدرجات الثلاث ودرجة النجاح المطلوبة.

المعالجة

  • التحقق من النطاق المسموح.
  • جمع الدرجات وحساب المتوسط.
  • مقارنة المتوسط بدرجة النجاح.

المخرجات

متوسط الدرجات وحالة الطالب وفق شرط النجاح المحدد.

المتطلبات

استقبال الدرجات والتحقق منها وحساب المتوسط وعرض النتيجة، مع رسائل واضحة وإدخال سهل واستجابة سريعة.

الخوارزمية المبدئية

  1. ابدأ واستقبل درجات المواد الثلاث.
  2. تحقق من صحة الدرجات.
  3. احسب المتوسط وقارنه بدرجة النجاح.
  4. اعرض المتوسط والحالة ثم انتهِ.

التحدي العملي

صمّم خطوات برنامج يحسب متوسط درجات طالب في عدد يختاره المستخدم من المواد. حدد المدخلات والمعالجة والمخرجات، واكتب الخوارزمية خطوة بخطوة، وفكر فيما سيحدث إذا لم يدخل المستخدم أي درجات أو أدخل درجة خارج النطاق. أنشئ ثلاث حالات اختبار على الأقل واكتب النتيجة المتوقعة لكل حالة. لا تبدأ بكتابة الكود قبل أن تتأكد من وضوح الحل.

إزاي تكتشف الأخطاء المنطقية؟

Logical Errors

مش كل خطأ في البرنامج بيمنع تشغيله. قد يرفض البرنامج الكود قبل أن يبدأ، أو يتوقف أثناء التنفيذ، أو يعمل حتى النهاية لكن يعرض نتيجة غير صحيحة. في هذه الحالة قد يكون السبب خطأ منطقيًا: صياغة الكود مقبولة، لكن خطوات الحل لا تعبّر عن المطلوب.

مقارنة أنواع الأخطاء

خطأ نحوي

Syntax Error

يخالف قواعد كتابة اللغة وقد يمنع البرنامج من البدء.

مثال: نسيان النقطتين بعد if في Python.

التعامل: تصحيح صياغة الكود.

خطأ وقت التشغيل

Runtime Error

يحدث أثناء التنفيذ وقد يوقف البرنامج.

مثال: القسمة على صفر.

التعامل: التحقق من العملية والقيم أثناء التنفيذ.

خطأ منطقي

Logical Error

يعمل البرنامج، لكن النتيجة غير صحيحة.

مثال: إضافة قيمة الخصم إلى السعر بدل طرحها.

التعامل: مقارنة النتيجة بالمتوقع ومراجعة خطوات الحل.

مثال حساب السعر بعد الخصم

قيمة الخصم = السعر × نسبة الخصم ÷ 100. السعر النهائي = السعر الأصلي − قيمة الخصم. إذا كان السعر 250 جنيهًا ونسبة الخصم 20%، فالخصم 50 جنيهًا والسعر النهائي 200 جنيه.

Software Testing Basics

هل البرنامج بيشتغل؟ ولا بيشتغل صح؟

قد يعرض برنامج المتوسط 80 لدرجات 80 و90 و70، لكنه قد يفشل مع الصفر أو قيمة غير صحيحة أو درجة خارج النطاق. Software Testing هي عملية فحص البرنامج والتحقق من تحقيقه للمتطلبات واكتشاف المشكلات قبل وصوله للمستخدمين أو أثناء تطويره.

يعني إيه Test Case؟

حالة الاختبار مجموعة بيانات وخطوات لاختبار وظيفة ومقارنة النتيجة الفعلية بالمتوقعة. وتشمل اسم الاختبار والمدخلات وخطوات التنفيذ والنتيجة المتوقعة والفعلية والحالة: ناجح أو فاشل.

أنواع حالات الاختبار

Normal Case

بيانات معتادة، مثل 80 و90 و70؛ المتوسط المتوقع 80.

Boundary Case

اختبار حدود النطاق 0 إلى 100، والقيم القريبة مثل 1 و99.

Invalid Input

درجة أكبر من 100 أو أقل من صفر أو نص بدل رقم. يرفضها البرنامج أو يعرض رسالة مناسبة حسب المتطلبات.

Edge Case

أرقام كبيرة جدًا، أو عدم إدخال بيانات، أو قيمة عشرية، أو تكرار القيم. قبولها أو رفضها يعتمد على متطلبات النظام.

Unit Testing

اختبار جزء صغير ومستقل من البرنامج، مثل دالة جمع رقمين:

def add_numbers(a, b):
    return a + b

result = add_numbers(10, 20)
print(result)

assert add_numbers(10, 20) == 30
assert add_numbers(5, 5) == 10
assert add_numbers(-2, 2) == 0

الناتج المتوقع 30. لو شرط من شروط assert غير صحيح، Python هتظهر خطأ يوضح إن الاختبار لم ينجح. بنختبر وظيفة صغيرة بدل انتظار اكتمال البرنامج كله.

مستويات الاختبار

Unit Testing

اختبار وحدة صغيرة، مثل دالة أو عملية حسابية.

Integration Testing

اختبار تعاون المكونات، مثل إرسال نموذج التسجيل بياناته لخدمة الحسابات.

System Testing

اختبار النظام بالكامل، مثل وظائف المكتبة من تسجيل الكتب إلى الاستعارة والإرجاع.

Acceptance Testing

التأكد من تلبية احتياجات المستخدم والمتطلبات المتفق عليها، مثل تجربة موظف المكتبة للنظام.

Test-Driven Development

TDD أسلوب تطوير نكتب فيه اختبار الوظيفة المطلوبة قبل كودها، ويمر بدورة تتكرر مع كل وظيفة:

Red

نكتب اختبار السلوك المطلوب، وغالبًا يفشل لأن الوظيفة غير موجودة بعد.

Green

نكتب أبسط كود يجعل الاختبار ينجح.

Refactor

نحسن تنظيم الكود وجودته مع الحفاظ على نجاح الاختبارات.

مهم تعرف إن TDD أسلوب تطوير، مش مجرد نوع اختبار.

هل الاختبار يضمن عدم وجود أخطاء؟

لا. نجاح كل الاختبارات المكتوبة مش دليل قاطع على خلو البرنامج من الأخطاء؛ قد توجد حالات لم نختبرها أو متطلبات لم نلاحظها أو مشكلات تظهر في ظروف معينة. لذلك ننوع الاختبارات ونفحص الحدود والمدخلات غير الصحيحة ونراجع النتائج ونعيد الاختبارات بعد تعديل الكود. الاختبار غير الجيد ممكن يفوّت المشكلة.

لحساب مجموع رقمين، نستقبل الرقم الأول، ثم الثاني، ثم نجمعهما، ثم نعرض الناتج. الخطوات دي اسمها Algorithm — خوارزمية. الخوارزمية هي الأساس اللي بنبني عليه الحلول البرمجية؛ بنحدد خطوات حل المشكلة قبل ما نحولها لكود.

يعني إيه Algorithm؟

الخوارزمية مجموعة من الخطوات المحددة والمرتبة والمنطقية لحل مشكلة أو تنفيذ مهمة. ببساطة، هي خطة الحل اللي بتقولنا هنعمل إيه وبأي ترتيب علشان نوصل للنتيجة المطلوبة.

مثال من الحياة اليومية: تحضير كوب شاي

  1. ابدأ وجهّز كوبًا.
  2. سخّن الماء.
  3. ضع الشاي في الكوب وأضف الماء الساخن.
  4. أضف السكر حسب الرغبة.
  5. قلّب المكونات.
  6. انتهِ.

دي خطوات مرتبة لمهمة معينة. في البرمجة نستخدم نفس الفكرة للعمليات الحسابية ومعالجة البيانات وبناء الأنظمة.

ليه بنستخدم الخوارزميات؟

تنظيم التفكير

نحدد خطوات الحل بدل كتابة كود عشوائي.

تقليل الأخطاء

نراجع الحل ونكتشف المشكلات قبل كتابة الكود.

تسهيل الفهم

يمكن فهم الفكرة دون معرفة لغة البرمجة المستخدمة.

إعادة الاستخدام

نستخدم منطق الحل نفسه في أكثر من مشروع.

مقارنة الحلول

نقارن الخوارزميات من حيث السرعة واستهلاك الموارد.

الفرق بين Algorithm وProgram

Algorithm هي خطوات الحل المنطقية. Program هو تنفيذ الحل باستخدام لغة برمجة معينة.

خطة الحل

Algorithm — الخوارزمية

تشرح الخطوات المنطقية وترتيبها، ولا ترتبط بلغة برمجة بعينها.

  1. استقبل رقمين.
  2. اجمع الرقمين.
  3. اعرض الناتج.

تنفيذ الخطة

Program — البرنامج

يحوّل خطوات الخوارزمية إلى تعليمات بلغة برمجة يمكن تشغيلها.

number1 = 10
number2 = 20

result = number1 + number2
print(result)

الناتج: 30. الخوارزمية تشرح الفكرة، والبرنامج يحولها إلى تعليمات بلغة برمجة.

خصائص الخوارزمية الجيدة

Definiteness — الوضوحخطوات محددة لا تحتمل الغموض.

«اجمع الرقم الأول مع الثاني» أوضح من «اعمل العملية المناسبة».

Input — المدخلاتالبيانات التي تستقبلها الخوارزمية.

قد تستقبل صفرًا أو أكثر؛ خوارزمية جمع رقمين تستقبل رقمين.

Output — المخرجاتنتائج مرتبطة بالمهمة.

في خوارزمية الجمع، الناتج هو مجموع الرقمين.

Finiteness — الانتهاءتنتهي بعد عدد محدود من الخطوات.

تصل إلى نهاية محددة ولا تستمر بلا نهاية.

Effectiveness — قابلية التنفيذخطوات بسيطة يمكن تنفيذها.

كل خطوة عملية وقابلة للتنفيذ بالفعل.

ملاحظة: دي الخصائص الأساسية لوصف الخوارزمية الجيدة، وقد تختلف طريقة عرضها أو تفصيلها بين المراجع.

طرق تمثيل الخوارزميات

Algorithm Representation Methods

بعد ما نحدد خطوات حل المشكلة، نحتاج طريقة واضحة لعرضها ومراجعتها ومشاركتها. تمثيل الخوارزمية يوضح ترتيب الخطوات قبل تحويلها إلى برنامج.

مقارنة طرق التمثيل الأربع

Natural Language — اللغة الطبيعية

خصائص الخوارزمية الجيدة

Characteristics of a Good Algorithm

الخوارزمية الجيدة مش مجرد خطوات مكتوبة؛ لازم تكون مفهومة، تستقبل البيانات المناسبة، تنتج النتيجة المطلوبة، وتنتهي، وتكون خطواتها قابلة للتنفيذ وصحيحة للمشكلة. هنطبق الخصائص الست على مثال مساحة مستطيل.

الخصائص الست

Definiteness — الوضوح والتحديدخطوات لا تحتمل تفسيرًا غامضًا.

صحيح: اقرأ الطول والعرض ثم اضربهما. غير صحيح: نفّذ العملية المناسبة؛ لأن نوع العملية غير محدد.

Input — المدخلاتتحديد البيانات المطلوبة.

مساحة المستطيل تحتاج إلى الطول والعرض. من دون تحديد كيفية توفير الأبعاد لا تكون المدخلات واضحة.

Output — المخرجاتالنتيجة المطلوبة من الحل.

المخرج هو قيمة المساحة. حسابها دون حفظها أو عرضها لا يحقق المطلوب بالكامل.

Finiteness — الانتهاءعدد محدود من الخطوات.

تحسب الخوارزمية المساحة مرة وتنتهي. التكرار بلا شرط توقف مثال غير صحيح.

Effectiveness — قابلية التنفيذكل خطوة عملية ويمكن تنفيذها.

ضرب الطول في العرض قابل للتنفيذ. اطلب من الكمبيوتر معرفة الأبعاد من تلقاء نفسه دون مصدر بيانات مثال غير عملي.

Correctness — الصحةإنتاج النتيجة الصحيحة لكل مدخل صالح.

المساحة = الطول × العرض. استخدام الجمع يعطي نتيجة أخرى، لذلك الخوارزمية غير صحيحة حتى لو كانت الخطوات واضحة.

الفرق بين الوضوح والصحة

واضحة وصحيحة

اقرأ الطول والعرض، احسب المساحة = الطول × العرض، ثم اعرضها.

واضحة لكنها غير صحيحة

اقرأ الطول والعرض، احسب المساحة = الطول + العرض. الخطوات واضحة لكن القانون لا يحسب المساحة.

غير واضحة

اقرأ الأبعاد ونفّذ الحساب المناسب. لم تحدد الخطوة أي حساب مطلوب.

تتبّع تنفيذ الخوارزميات

Algorithm Tracing

مقدمة: يعني إيه تتبّع خوارزمية؟

تخيل إن عندك خوارزمية بتستقبل رقمين، تجمعهم، وبعد كده تعرض الناتج. بدل ما تشغّل الكود وتستنى النتيجة، تقدر تمشي على الخطوات واحدة واحدة، وتتابع إيه اللي بيحصل داخل البرنامج. العملية دي اسمها Algorithm Tracing، يعني تتبّع تنفيذ الخوارزمية.

  • تفهم البرنامج بينفذ إيه بالترتيب.
  • تعرف قيمة المتغيرات في كل خطوة.
  • تكتشف الأخطاء المنطقية.
  • تتوقع الناتج قبل تشغيل البرنامج.
  • تفهم الحلقات والشروط بشكل أفضل.

أولًا: يعني إيه Variable؟

المتغير (Variable) مكان بنستخدمه لتخزين قيمة معينة أثناء تنفيذ البرنامج. في age = 18 خزّنا 18 في age؛ ولو أسندنا إليه 20 أصبحت هي القيمة الحالية. المتغير ممكن تتغير قيمته أثناء تنفيذ الخوارزمية، وده اللي لازم نتابعه.

OUTPUT C

القيمة تتغير من 10 إلى 15 ثم 30. التعبير X = X + 5 يعني احسب الطرف اليمين وبعدها خزّن الناتج في X، مش مساواة رياضية بين الطرفين.

رابعًا: تتبّع العمليات الحسابية

A = 4
B = 6
C = A + B * 2

الضرب يتنفذ قبل الجمع: B × 2 = 12، ثم A + 12 = 16. ولو استخدمنا الأقواس: C = (A + B) * 2، يكون الناتج 20.

خامسًا: تتبّع الشروط

X = 12
IF X > 10
    OUTPUT "Large"
ELSE
    OUTPUT "Small"
END IF
  1. X تساوي 12.
  2. نختبر هل 12 أكبر من 10؟
  3. الإجابة True، فننفذ IF.
  4. الناتج Large، وفرع ELSE لا يتنفذ.

سابعًا: أخطاء شائعة أثناء التتبّع

  1. نسيان تسجيل القيمة الجديدة بعد تحديث المتغير.
  2. تنفيذ الخطوات بترتيب مختلف عن ترتيب الخوارزمية.
  3. تجاهل أولوية العمليات والأقواس.
  4. تنفيذ IF وELSE معًا بدل اختيار الفرع المناسب.
  5. نسيان إعادة اختبار شرط الحلقة بعد كل تكرار.
